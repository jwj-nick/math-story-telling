## 4. ★ 계획을 바꾸는 발견 — "추출"이 아니라 "지면 재구성"이다

파일럿 대상 `p2.html`(지수법칙)의 실제 문항을 열어 보고 확인한 사실:

```html
<p class="ask"><span class="qi">(1)</span><span class="eq">a³ × a⁴ = a□</span> 의 지수 □?</p>
<input id="a11"> → 정답 7
```
```js
prob('c4',[P('b43c','a43c',6,…),P('b43a','a43a',3,…),P('b43b','a43b',4,…)],'w43');
// 한 문항이 계수칸·지수칸 등 여러 빈칸으로 쪼개져 있다
```

> **중2 앱 문항은 "숫자 빈칸 채우기"로 분해되어 있다.** 폰 입력에 최적화된 형식이다.
> 종이에서는 `3a² × 2a` 의 **계수 6, 지수 3을 따로 묻는 게 아니라** `6a³` 를 통째로 쓰게 해야 한다.

**따라서 이 프로젝트의 본체는 파일 변환이 아니라 발문 재작성이다.** 다행히 구조는 이렇게 갈린다:

| 요소 | 방법 | 신뢰도 |
|---|---|---|
| 정답(원자 값) | **스크립트 추출** — `P(...)`/`MJ.check(...)`를 정규식으로 | 결정적 ✅ |
| 문항 본문·힌트·풀이·`.tip`/`.why` | **스크립트 추출** | 결정적 ✅ |
| **지면 발문** (`stem_print`) | **LLM 재작성** — §5 발문 규약 적용 | 검토 필요 ⚠️ |
| **지면 정답** (`answer_print`) | 원자 값 **합성** (계수 6 + 지수 3 → `6a³`) | 원자 값과 대조로 검증 가능 ✅ |

원자 정답이 결정적으로 확보되므로, **재작성된 발문·정답이 원본과 어긋나면 기계가 잡아낸다.** 이게 §11 검증의 근거다.

중1(세대 A)은 이미 서술형/단답형이라 발문 재작성 부담이 훨씬 작다. **비용은 중2에 몰려 있다.**

## 5. ★ 발문 규약 (D6 — "해석에 오해 없고 단위 명확")

지면 문항이 지켜야 할 규칙. `PRINT_PRINCIPLES.md`에 SSOT로 넣고 `/se-audit-app` 프린트 게이트로 검사한다.

**R1. 요구문을 명시한다.** `□`나 빈칸에 기대지 않는다.
- ✗ `a³ × a⁴ = a□ 의 지수 □?`
- ✅ `a³ × a⁴ 을 간단히 하시오.`  (답란: `답 ________`)

**R2. 한 문항 = 한 요구.** 요구가 둘이면 (1)(2)로 나눈다. 답란도 나눈다.

**R3. 답의 형태를 지정한다.** 형태가 여러 개면 어느 것이 맞는지 학생이 모른다 — 자기채점이 무너지는 1순위 원인.
- `$a^n$ 꼴로`, `기약분수로`, `x = ` 꼴로, `소수 첫째 자리까지 반올림하여`

**R4. 단위를 못 박는다.**
- 문제문에 단위 조건을 쓰고, **답란에 단위를 미리 인쇄한다**: `답 _______ cm²`
- 단위가 없는 순수 수치면 `답 _______ (단위 없음)`
- 각도 `°`, 개수 `개`, 길이 `cm`, 넓이 `cm²`, 부피 `cm³`, 확률은 `기약분수` — 단원별 표준 단위를 은행 스키마에 고정한다

**R5. 앱 의존 표현을 금지한다.** "버튼을 눌러", "슬라이더를 움직여", "위 그림에서 값을 바꿔" → 전부 제거. 그림 참조는 "오른쪽 그림에서".

**R6. 그림은 문항 옆에 인쇄한다.** 인라인 SVG를 그대로 쓴다. 그림이 다음 장으로 넘어가면 안 된다(문항 단위 `page-break-inside: avoid`).

**R7. 지시문은 해요체.** `10_system/10_principles/WRITING_VOICE.md` 준수. 단, **문제 발문 자체는 시험 문투(`구하시오`, `간단히 하시오`)를 허용**한다 — 실제 시험지와 형식을 맞추는 것이 시험 대비 목적에 부합한다. 안내문·오개념 카드·격려문은 해요체.

## 7. 자기채점 설계 (D3 — 학생 스스로)

혼자 채점하면 실패 지점이 셋이다. 각각에 대응한다.

| 실패 | 대응 |
|---|---|
| **동치 표현을 오답 처리** ($\frac12$ vs $0.5$, $6a^3$ vs $6\times a^3$) | 정답지에 **허용 정답을 함께 인쇄**: `답 6a³  (같은 답: 6·a³)`. 은행 스키마에 `answer_accept[]` |
| **틀린 걸 맞다고 넘김** | 답의 형태를 R3으로 못 박아 애매함을 없앤다 |
| **왜 틀렸는지 안 보고 넘김** | 진단표에서 **○/△/✗ 3단계**로 구분시킨다 |

**채점 기호 3단계 — 이게 이 설계의 핵심이다.**

| 기호 | 뜻 | 다음 행동 |
|---|---|---|
| **○** | 맞음 | 넘어간다 |
| **△** | **답은 틀렸는데 어디서 틀렸는지 내가 안다** (계산 실수 등) | 그 자리에서 다시 푼다. 오개념 아님 |
| **✗** | **왜 틀렸는지 모르겠다 / 손도 못 댔다** | **오개념 카드 → 해당 번호를 읽는다** → 진단표에 오개념 번호 기록 |

△와 ✗를 가르는 것이 메타인지 훈련이고, ✗만 오개념 로그에 쌓인다. **점수는 기록하지 않는다.** (q03 §5-③ — 남이 지적하는 게 아니라 자기 패턴을 자기가 본다)

**정답지 배부 규약:** 정답지(A)·해설지(S)는 **문제지와 다른 종이**로, 문제를 다 푼 뒤에 꺼낸다. 앱에서 애써 만들려던 "정답까지의 거리"가 여기서 공짜로 확보된다.

## 12. 검증 전략

**모든 문항은 원본과 대조로 검증한다.** 손으로 다시 쓰면 검증된 수학에 오류가 새로 들어간다.

`verify_bank.py`가 검사하는 것:
1. **문항 수** — 은행 문항 수 == 원본 `.pq`/`.card` 수
2. **정답 원자** — `answer_atoms` == 원본 `P(...)`/`MJ.check(...)` 값 (문자열 비교)
3. **합성 정답** — `answer_print`가 원자들과 모순되지 않는가 (예: 원자 [6,3] ↔ `6a³` 의 계수·지수 파싱 일치)
4. **§5 규약 린트** — `stem_print`에 `□`, "버튼", "슬라이더" 등 앱 의존 표현이 남았는가 / `answer_format` 누락 / 단위 필요 단원인데 `answer_unit` 없음
5. **오개념 무결성** — 태그가 카탈로그에 존재하는가 / **카드 본문에 정답이 새지 않았는가**
6. **어투** — 안내문·오개념 카드에 반말이 있는가 (`WRITING_VOICE.md`)

\+ 수학 정확성은 기존 `/se-audit-math`로 표본 검사. `/se-audit-app`에 **프린트 게이트** 항목을 추가한다.
